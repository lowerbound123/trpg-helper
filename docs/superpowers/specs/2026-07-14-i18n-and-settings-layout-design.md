# I18n And Settings Layout Design

## Scope

This change adds complete Chinese and English localization to user-facing UI, widens the Settings dialog, and swaps the manager status display with the Settings action. It does not translate file names, project names, Asset names, tags, paths, model identifiers, format identifiers, or other user and data values.

## Layout

- Settings uses `width: min(1440px, calc(100vw - 32px))` and retains a viewport-constrained maximum height.
- The manager header action order becomes status first and Settings last.
- Existing responsive Settings behavior remains: two section columns at wide sizes and one column below 900px.

## Locale Selection

- `[application]` gains `locale = "auto"`.
- Accepted values are `auto`, `zh-CN`, and `en-US`.
- `auto` resolves from the system/browser locale at application startup. Locales beginning with `zh` resolve to `zh-CN`; all others resolve to `en-US`.
- Settings General exposes an Auto / 简体中文 / English selector.
- Saving locale does not mutate the active Vue I18n composer. The new locale takes effect after application restart.
- Desktop startup reads `~/Documents/trpg-helper/configuration.toml`; browser development uses the existing configuration override path.

## Translation Architecture

- Add Vue I18n in Composition API mode and install it before mounting the root app.
- Locale resources live in dedicated `zh-CN.ts` and `en-US.ts` modules.
- Every message key uses flat `UPPER_SNAKE_CASE`, for example `SETTINGS_TITLE`, `EXPORT_FAILED`, and `ITEM_COUNT`.
- Natural-language source strings exist only in locale resource files and test fixtures.
- Components and composables use `useI18n().t()` or a shared non-component translator for store/backend-adjacent status generation.
- Interpolation carries dynamic values such as `{name}`, `{count}`, and `{percent}`. Dynamic values are never translated.
- Counts use Vue I18n plural messages where singular and plural differ in English.

## Coverage

Localization covers all visible application-owned UI:

- Manager, Handout editor, Token editor, Settings, export panels, inspectors, dialogs, tabs, buttons, labels, empty states, progress, notifications, and status badges.
- Context menus, tooltips, placeholders, accessible names, titles, and ARIA labels.
- Runtime status and operation errors generated by stores and composables.
- VueFinder is configured with its bundled `zhCN` or `en` locale to match the application locale.

The following remain unchanged:

- File, folder, project, layer, Asset, font, and Token item names.
- User-entered text, tags, paths, color values, format identifiers, and model identifiers.
- Log records and low-level Rust diagnostics.

## Error Handling

- Raw backend error strings are written to the appropriate log scope.
- UI surfaces a localized operation-specific message, optionally interpolating safe dynamic context such as a file name.
- Raw Rust error text is not rendered directly in normal UI, preventing Chinese backend diagnostics from leaking into English mode.
- Unknown failures use a localized generic error and retain the raw value only in logs.

## Verification

- Locale key parity test: Chinese and English key sets must match exactly.
- Key format test: every key must match `^[A-Z][A-Z0-9_]*$`.
- Locale resolution tests cover Chinese system locales, non-Chinese locales, explicit overrides, and invalid configuration.
- Source audit test rejects CJK text outside locale resources and approved non-UI fixtures.
- Source audit test rejects direct user-facing English literals in Vue templates and known UI string APIs.
- Component tests cover manager action ordering, wider Settings layout, locale selector persistence, restart notice, VueFinder locale selection, interpolation, pluralization, and localized errors.
- Full verification runs Vitest, typecheck, production build, Rust tests, and the existing Tauri debug bundle command.

## Migration Strategy

1. Add configuration and locale bootstrap with parity tests.
2. Add Vue I18n and VueFinder locale wiring.
3. Migrate shell and Settings first, including the requested layout changes.
4. Migrate Handout, Token, dialogs, menus, status, errors, tooltips, and accessibility text by domain.
5. Enable strict source-audit tests after migration so future raw UI strings fail CI.
6. Update `DOC.md` with locale configuration and maintenance rules.
